# Project InSight（PIS）

PIS 是一个面向小团队的项目计划制定与追踪 Web 应用。它基于实用的项目管理经验，提供简单、高效、可扩展的项目管理功能。

上游原文在项目列表、工作区任务表、甘特图三处配有界面截图（`files/project-info.png`、`files/wps.png`、`files/gatt.png`）。图片留在 PIS 仓库，本条目不转载。

## 1 设计背景

原始需求是「实现项目计划的制定和追踪」。

现成工具对不上这个需求：

- 使用 Project 太繁重。
- 使用 Excel 无法处理依赖。
- 两者都无法通过 Web 进行团队协作。

因此，为了制定某个项目的计划，直接使用 Trae 开发一个 Web 版的项目计划制定与追踪工具，用来实践最有用的项目管理经验。

## 2 计划管理经验

项目管理里，计划管理的范畴很大。这里只展开最基本、最实用的方法，主要回答四件事：

1. 如何拆解任务，把总体目标拆成多个小目标，并确保拆解合理？
2. 如何让拆解后的任务可执行，并让依赖关系合适？
3. 如何在执行过程中追踪计划、调整计划、识别计划风险？
4. 目标可能延期时，应该如何处理？

### 2.1 任务分解（WBS 分解）

1. 计划总目标分解成 N 个小目标。无论大目标还是小目标，都必须可测量，有明确的完成标准。
2. 同一级目标之间一定是并列的兄弟关系，避免出现「男人、女人、老人」这样不并列的分解。
3. 要问自己：完成了这 N 个小目标，大目标是否就完整了？同样，N 个小目标还要继续分解到更小的目标。
4. 要渐进明细。两周内的工作分解到两三天粒度；两周后的工作可以先做粗粒度，再逐步分解。

**输出物**：工作分解 WBS 和基本的顺序。到这里，工作范围和事项拆解就识别出来了。

### 2.2 起点、终点，以及中间任务的依赖

1. **起点**：一般用「开工会」作为起点，它也是依赖的总起点。
2. **终点**：任务的完成时间。安排好 WBS 和依赖后，务必紧盯这个终点。
3. **逻辑依赖**：例如先设计再研发。
4. **资源依赖**：例如同一个负责人。

**输出物**：计划的静态版。经过任务分解、设置起点、终点和依赖，就可以开始追踪任务。

### 2.3 任务追踪

计划就是用来变的，就是用来更新的。有两种必须做的更新：

1. **变化带来的更新**。人员、需求、条件、资源等发生变化时，要及时刷新，并在刷新时考虑对目标的影响。
2. **渐进明细带来的更新**。两周后的工作原先看不清、时间范围大；随着时间推移，逐渐分解到更细粒度、更准确的时间点。

计划变更的原则：

1. 计划就是用来更新的。更新计划的过程，就是保证任务终点能够完成的过程。
2. 最终目标不能改变。改变最终目标已经超出项目经理的职责范围。若不得不改变目标，必须向上沟通并得到批准。
3. 某项任务不能到最后一天才发现因某种原因完不成，必须提前识别，否则谁也没有办法完成它。
4. 更不能存在过去时间点的任务。常有项目经理投诉「这是上个月要完成的，现在还没有做完」——这个逻辑不成立。
5. 追踪过程中只能调整时长和依赖关系，不能手工调整开始时间和终止时间。如果发现影响总进度和关键里程碑，就要采取措施。

**输出物**：不断调整的计划。一般一周至少调整两次。人员的工作目标和进展、执行风险，至少通过周报通报；关键期用日报通报。

### 2.4 赶工的六条措施

计划变更造成目标可能延期时：

1. 延迟工作时长，把每天和周末的时间也用上。
2. 任务并行：多项任务同时进行，切开关键路径任务。
3. 减范围：时间不能变，质量不能变，能变的只有范围。
4. 用好资源和设备。
5. 用专家力量。
6. 用好方法提高质量，减少返工。

**输出物**：赶工强化后的计划。

## 3 主要功能

设计文档把「项目计划的制定和追踪」拆成五条可实现的能力：

1. 多层级工作分解：增删改、缩进与排序、WBS 编码、父节点日期汇总。
2. 项目开工会作为无前置任务的默认起点。
3. 用工作日工期、资源与前置依赖安排工作。起止时间由排期引擎推算，而不是手填。
4. 项目初验点，并形成甘特图。
5. 过程中调整工期或依赖后自动重算，并指出是否影响初验。

### 3.1 项目列表

在项目列表可以查看已有项目，并新建、删除项目。新建时填写名称、可选代号、描述、开工会、初验点。

### 3.2 项目工作区

工作区里进行任务分解、计划调整与追踪，并显示项目甘特图。

#### 3.2.1 工作分解与任务字段

任务类型为汇总（SUMMARY）、工作项（TASK）、里程碑（MILESTONE）。

任务表支持：

- 行内改名称、时长、资源（自由文本）、前级依赖和进度。
- 上移、下移、缩进、升级。
- 在下方插入同级任务。

缩进时，若上一兄弟不是汇总节点，会把它提升为 SUMMARY，并把原来挂在它身上的依赖边转接到新子任务，避免后续任务突然失去前级。WBS 编码在结构变化后按显示顺序重算。

插入同级任务时，若未手选前级，会默认继承显示顺序中最近的一个可参与依赖图的任务。开工会除外的初验点不作为自动前级。

#### 3.2.2 依赖与校验

- 依赖类型只创建 FS。
- 依赖不能成环。
- 必须有从起点到终点的路径。

#### 3.2.3 甘特图

甘特图为自研渲染：

- 左侧 WBS 列，右侧按日时间轴；周末与节假日用底色区分。
- 条形表示任务：关键路径、已完成用不同颜色，条内按进度填充。
- 菱形表示里程碑。
- SVG 折线表示依赖。
- 虚线标出开工会、初验点和今日。

上游在下一步里把当前甘特描述为只读时间轴加点击编辑。拖拽改依赖、长列表虚拟化，以及提交前用同一份引擎做本地预览，均为「未实现」（见第 5.7 节）。

### 3.3 尚未做成功能的界面（未实现）

- 顶栏「资源」「审计」「用户」没有链接。
- 用户区写死为 `zhenggsh` /「SSO 已登录」。
- 退出、个人设置按钮没有处理函数。
- 没有登录页、成员邀请或角色鉴权。

## 4 主要系统架构和实现

### 4.1 分层

```
浏览器
  ProjectList / Workspace（甘特图、任务表、设置、对话框）
        │  Server Actions（"use server"）
Next.js 服务端
  server/actions/*     入参检查与 revalidatePath
  server/plan.ts       事务：变更 → 校验 → 重算 → 回写派生字段 → 审计
  server/workspace.ts  读库后再算一遍排期，组装视图（不落库）
  lib/scheduler/*      日历、拓扑、正逆推、汇总展开、冲击报告（纯函数）
  lib/validation/*     V1–V4（纯函数）
        │  Prisma 7 + better-sqlite3
SQLite（DATABASE_URL，缺省 file:./dev.db）
```

### 4.2 技术栈

以 `package.json` 为准：

- Next.js 16.4.4
- React 19.3
- TypeScript
- Tailwind CSS 4
- Prisma 7.10 与 `@prisma/adapter-better-sqlite3`
- Vitest 4

`zod` 在依赖中，`src/` 下没有引用。入参检查写在各个 Action 里：空名称、日期格式、初验不早于开工会、枚举取值等。`next.config.ts` 把 `better-sqlite3` 标为服务端外部包。

### 4.3 写路径

`applyPlanChange` 在一条事务里完成：

1. 读变更前计划。
2. 执行 `mutate`。
3. 用同一份 `validatePlan` 复算。
4. 阻断项，或未确认的建议项，抛 `PlanValidationFailure` 并回滚。
5. 否则 `computeSchedule`，并把 `plannedStart` / `plannedEnd` / `isCritical` / `totalFloatDays` / `scheduleSource` 写回任务。
6. 插入 `AuditLog`。

页面使用 `dynamic = "force-dynamic"`。写成功后 `revalidatePath`。客户端不在浏览器里跑排期引擎，编辑都要等服务端往返。打开工作区时 `loadWorkspace` 会再算一次用于展示，因此图上的日期以当次计算结果为准。

### 4.4 排期引擎

`lib/scheduler` 零 IO。

- `calendar.ts`：用位掩码和节假日集合做工作日判断、顺延和工作日加减。工期含首日：1 天则起止为同一天。
- `topo.ts`：做 Kahn 拓扑并返回环。
- `dependency-expand.ts`：把「依赖汇总节点」展开成叶子边。
- `impact.ts`：对比变更前后快照，给出余量差、日期变化和新旧关键任务。

`index.test.ts` 覆盖：单链 FS、滞后、菱形会合、节假日、MSO 吸附、环、余量为正 / 零 / 负、初验点锚定与被前级驱动、汇总 roll-up、依赖汇总节点。

### 4.5 校验

`lib/validation` 同样是纯函数。`index.test.ts` 覆盖 V1–V4 的主要正反例。服务端是权威校验。任务表在选前级时会在前端排除会形成自环的候选（自身与后代），环的最终判定仍在服务端。

V5 / V6 扫描为「未实现」，见第 5.8 节。

### 4.6 数据模型

`prisma/schema.prisma` 已建表：`User`、`ProjectMember`、`Project`、`Holiday`、`Task`、`Dependency`、`AuditLog`。

已标明但未接通的部分：

- 注释写明 v1 未启用登录。用户与成员只是预留结构，业务代码没有创建用户或检查角色。登录与角色鉴权为「未实现」。
- 资源是 `Task.assignee` 字符串，没有 `TaskAssignee`。成员分配为「未实现」。
- 没有基线表，没有扫描报告表。基线与扫描报告为「未实现」。
- `Task.version` 有字段，更新语句没有按 version 做条件写入。乐观锁为「未实现」。
- `AuditLog` 没有操作者外键，影响信息放在 `payload` JSON 字符串里。

Prisma Client 生成到 `src/generated/prisma`（已 gitignore）。仓库没有 `prisma/migrations`，脚本是 `db:push` / `db:studio`。

### 4.7 目录与测试

- 页面在 `src/app`。
- 工作区组件在 `src/components/workspace`。
- 项目列表在 `src/components/project`。

测试只有排期与校验这两组 Vitest 单测，没有 Server Action、WBS 重编号或界面测试。近期提交为脚手架初始化加上当前这一版计划功能（`init`），没有更细的功能分批记录。

## 5 下一步开发建议

下列事项都对应代码或设计文档里已经露出、但尚未接上的缺口。除另行说明外，这些能力当前均为「未实现」。

### 5.1 补上真实身份与权限（未实现）

顶栏用户、退出和个人设置是静态界面；「资源 / 审计 / 用户」不可点击。`User`、`ProjectMember` 和 `Role`（OWNER / PM / MEMBER / VIEWER）已建模却未被 Action 使用。写操作目前任何人打开页面即可执行。应先接登录，再在 `runChange` 入口按项目角色拒绝越权，并让顶栏导航指向真实页面。

### 5.2 把已经写入的审计展示出来（未实现）

`applyPlanChange` 会记 action、目标、已确认的规则编号和冲击摘要，但没有读取界面。审计页至少应按项目、时间倒序展示这些 payload，否则「确认后记入审计」在产品上不可见。

### 5.3 补齐并发控制（未实现）

`Task.version` 已存在，更新没有 `where: { id, version }`，也没有冲突后的刷新提示。多人同时改同一项目时，后写会覆盖先写。设计文档里的乐观锁可以直接落在 `applyPlanChange` 上。

### 5.4 让汇总进度与引擎结果一致（未实现）

`computeSchedule` 会按子节点工期加权算出汇总 `progressPct`。`persistSchedule` 不写该字段。`loadWorkspace` 展示的是库里的 `task.progressPct`。父节点进度因此不会随子节点填报更新。要么回写派生进度，要么在视图层改用本次排期结果。

### 5.5 用上已声明但未调用的 zod（未实现）

依赖已安装，Action 仍是手写判断，和设计文档「字段格式交给 zod、业务规则交给 validatePlan」不一致。把 `CreateProjectInput`、`UpdateTaskInput` 等收成共享 schema，可避免前后端各写一套范围检查。

### 5.6 扩大测试面（未实现）

排期与 V1–V4 有单测。事务回滚、WBS 重编号、缩进时的依赖转接、自动前级、初验点锚点不可删，都没有测试。这些分支集中在 `server/plan.ts` 与 `server/actions/task.ts`，适合先补集成测试，再考虑浏览器级流程：建项目 → 插任务 → 改工期 → 看到初验余量变化。

### 5.7 甘特图与本地预览（未实现）

图是只读时间轴加点击编辑，没有拖拽改依赖，没有长列表虚拟化。引擎已经是纯函数，但每次编辑都等 Server Action。可在提交前用同一份 `computeSchedule` / `validatePlan` 做本地预览，减少「处理中」往返。虚拟化留到单项目任务量上来之后再做。本地预览当前为「未实现」。
