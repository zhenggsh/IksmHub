# Project InSight（PIS）

> 来源：[zhenggsh/PIS](https://github.com/zhenggsh/PIS) `mydoc/PIC_intro.md`（master）
> 收录说明：按 IksmHub 知识条目重排。能力边界以该文为准；设计文档里尚未编码的能力保持「未实现」标记，不补充仓库外信息。

PIS 是一个面向小团队的项目计划制定与追踪 Web 应用。当前仓库是 **Next.js 全栈单体**：用工作分解（WBS）、完成-开始（FS）依赖和工作日历推算计划起止时间，在甘特图上展示关键路径，并在每次变更后判断是否冲击项目初验点。

仓库里同时存在两层材料：

- `docs/project-system-design.md`（v1.1，2026-11-03，状态为待评审）描述目标设计。
- `src/` 与 `prisma/schema.prisma` 是已经落地的实现。

下文以代码为准。设计文档中尚未编码的能力单独标出。根目录 `README.md` 仍是 `create-next-app` 模板，没有描述上述业务。应用自身的产品说明以页面文案和设计文档为准：站点标题为「PIS · Project InSight」，副标题为「目标为中心」。

## 1 设计背景

原始需求是「实现项目计划的制定和追踪」。设计文档把它拆成五条可实现的能力。

### 1.1 五条能力

1. 多层级工作分解：增删改、缩进与排序、WBS 编码、父节点日期汇总。
2. 项目开工会作为无前置任务的默认起点。
3. 用工作日工期、资源与前置依赖安排工作，起止时间由排期引擎推算，而不是手填。
4. 项目初验点，并形成甘特图。
5. 过程中调整工期或依赖后自动重算，并指出是否影响初验。

### 1.2 v1.1 补充

v1.1 补充了任务的十个用户字段：序号、进度、项目描述、起止时间、时长、资源、前级依赖、是否里程碑、进展描述。

同时定义三级校验：

- **必须遵循**：V1 缺前级依赖、V2 循环依赖。
- **建议遵循**：V3 叶子工期粒度、V4 过程任务不得直接改起止日期。
- **自动扫描**：V5 / V6，可选外部模型。

### 1.3 技术选型

技术选型写在设计文档第 2 章。复杂度集中在排期算法和甘特图，而不是高并发，因此选定 TypeScript 全栈单体（Next.js App Router + Prisma）。排期与校验做成无 IO 的纯函数。

本地数据库用 SQLite。枚举和日期以字符串落库，避免 SQLite 不支持原生 enum，以及时区换算歧义。生产侧设计为 PostgreSQL，代码里尚未切换。

## 2 主要功能

当前可运行的页面只有两条路由：

- `/` 项目列表
- `/projects/[projectId]` 项目工作区

工作区有三个页签：甘特图、任务表、项目设置。

### 2.1 项目

列表可新建、删除项目。新建时填写：

- 名称
- 可选代号（缺省自动生成 `PIS-` 前缀）
- 描述
- 开工会
- 初验点
- 工作周掩码
- 叶子工期上限（默认 3 个工作日）

初验点早于开工会会被拒绝。创建后自动写入两个零工期里程碑：「项目开工会」（`isKickoff`，WBS `1`）和「项目初验点」（`isPreAccept`，WBS `2`），并立刻跑一次排期。这两个锚点任务不能删除，日期在项目设置里改。

项目状态取值为：规划中、执行中、暂停、已关闭。

### 2.2 工作分解与任务字段

任务类型为汇总（SUMMARY）、工作项（TASK）、里程碑（MILESTONE）。

任务表支持：

- 行内改名称、时长、资源（自由文本）、前级依赖和进度
- 上移、下移、缩进、升级
- 在下方插入同级任务

缩进时，若上一兄弟不是汇总节点，会把它提升为 SUMMARY，并把原来挂在它身上的依赖边转接到新子任务，避免后续任务突然失去前级。WBS 编码在结构变化后按显示顺序重算。

插入同级任务时，若未手选前级，会默认继承显示顺序中最近的一个可参与依赖图的任务。开工会除外的初验点不作为自动前级。

任务对话框还可维护描述、进展描述、ASAP /「不早于」（MSO）约束。对已开工任务强制指定起始日时，不直接写 `plannedStart`，而是转成 MSO 约束，并触发 V4 确认。进度达到 100 时状态记为已完成，并写入实际开始/结束日期（取服务器当天）。

### 2.3 依赖与校验

依赖类型在领域常量里预留了 FS / SS / FF / SF。写入路径只创建 FS，并支持滞后量 `lagDays`（可为负）。

约束：

- 汇总节点不能作为后续任务。
- 把汇总节点当作前级，引擎会展开成「依赖其下全部叶子任务」，取最晚结束。
- 依赖包含自身的汇总会判为环。

保存前在同一事务里跑 `validatePlan`：

| 规则 | 级别 | 当前行为 |
| --- | --- | --- |
| V1 除开工会、初验点锚点和汇总节点外，必须有前级依赖 | 阻断 | 拒绝保存 |
| V2 循环依赖 | 阻断 | 拒绝保存，并返回环路任务 |
| V3 叶子工作项工期超过项目 `maxLeafDays` | 建议 | 确认后可保存；一周内（≤5 天）与更长工期文案不同 |
| V4 已开工或已有实际开始日的任务，补丁里直接出现计划起止日期 | 建议 | 确认后以 MSO 落地 |

只有本次新引入的建议项需要确认；变更前已经存在的建议项不会反复打断。V4 每次强制改日期都要确认。确认过的规则编号写入 `AuditLog.payload`。

V5 / V6 与 `aiScanEnabled` 只留了字段和类型位，没有扫描实现，界面也不会发起外部模型调用。

### 2.4 排期与初验冲击

`computeSchedule` 按工作日做正推。默认周一至周五，可改掩码，可加节假日。

- FS：前级结束后的下一个工作日，再加滞后。
- 里程碑零工期。
- MSO 日期落在非工作日时，顺延到下一工作日。
- 未给初验点配前级时，它锚定在目标初验日，不计入预计完工；配了前级则由前级驱动，目标日仍作逆推锚点。
- 逆推得到总浮动时间，浮动 ≤ 0 的任务标为关键路径。
- 汇总节点的起止取子节点包络。

项目头展示：开工会、初验点、预计完工、余量（工作日）、关键任务数。

变更成功后，结果面板用绿 / 黄 / 红说明：初验是否受冲击、余量变化、新进入关键路径的任务，以及最多五条起止时间变化。

### 2.5 甘特图与导出

甘特图为自研渲染：

- 左侧 WBS 列，右侧按日时间轴；周末与节假日用底色区分。
- 条形表示任务（关键路径、已完成用不同颜色，条内按进度填充）。
- 菱形表示里程碑。
- SVG 折线表示依赖。
- 虚线标出开工会、初验点和今日。
- 点击条或标签打开任务编辑。

甘特图本身不能拖拽改期或连线。

任务表支持列筛选、汇总折叠、变更后高亮受影响行，以及导出当前筛选结果为 UTF-8 CSV（带 BOM）。没有 PNG、Excel 或 MS Project XML 导出。

### 2.6 尚未做成功能的界面

- 顶栏「资源」「审计」「用户」没有链接。
- 用户区写死为 `zhenggsh` /「SSO 已登录」。
- 退出、个人设置按钮没有处理函数。
- 没有登录页、成员邀请或角色鉴权。

## 3 主要系统架构和实现

### 3.1 分层

```
浏览器
  ProjectList / Workspace（甘特图、任务表、设置、对话框）
        │  Server Actions（"use server"）
Next.js 服务端
  server/actions/*     入参检查与 revalidatePath
  server/plan.ts       事务：变更 → 校验 → 重算 → 回写派生字段 → 审计
  server/workspace.ts  读库后再算一遍排期，组装视图（不落库）
  lib/scheduler/*      日历、拓扑、正逆推、汇总展开、冲击报告（纯函数）
  lib/validation/*     V1–V4（纯函数）
        │  Prisma 7 + better-sqlite3
SQLite（DATABASE_URL，缺省 file:./dev.db）
```

### 3.2 技术栈

以 `package.json` 为准：

- Next.js 16.4.4
- React 19.3
- TypeScript
- Tailwind CSS 4
- Prisma 7.10 与 `@prisma/adapter-better-sqlite3`
- Vitest 4

`zod` 在依赖中，`src/` 下没有引用。入参检查写在各个 Action 里（空名称、日期格式、初验不早于开工会、枚举取值等）。`next.config.ts` 把 `better-sqlite3` 标为服务端外部包。

### 3.3 写路径

`applyPlanChange` 在一条事务里完成：

1. 读变更前计划。
2. 执行 `mutate`。
3. 用同一份 `validatePlan` 复算。
4. 阻断项，或未确认的建议项，抛 `PlanValidationFailure` 并回滚。
5. 否则 `computeSchedule`，并把 `plannedStart` / `plannedEnd` / `isCritical` / `totalFloatDays` / `scheduleSource` 写回任务。
6. 插入 `AuditLog`。

页面使用 `dynamic = "force-dynamic"`。写成功后 `revalidatePath`。客户端不在浏览器里跑排期引擎，编辑都要等服务端往返。打开工作区时 `loadWorkspace` 会再算一次用于展示，因此图上的日期以当次计算结果为准。

### 3.4 排期引擎

`lib/scheduler` 零 IO。

- `calendar.ts`：用位掩码和节假日集合做工作日判断、顺延和工作日加减。工期含首日：1 天则起止为同一天。
- `topo.ts`：Kahn 拓扑，并返回环。
- `dependency-expand.ts`：把「依赖汇总节点」展开成叶子边。
- `impact.ts`：对比变更前后快照，给出余量差、日期变化和新旧关键任务。

`index.test.ts` 覆盖：单链 FS、滞后、菱形会合、节假日、MSO 吸附、环、余量为正 / 零 / 负、初验点锚定与被前级驱动、汇总 roll-up、依赖汇总节点。

### 3.5 校验

`lib/validation` 同样是纯函数。`index.test.ts` 覆盖 V1–V4 的主要正反例。服务端是权威校验。任务表在选前级时会在前端排除会形成自环的候选（自身与后代），环的最终判定仍在服务端。

### 3.6 数据模型

`prisma/schema.prisma` 已建表：`User`、`ProjectMember`、`Project`、`Holiday`、`Task`、`Dependency`、`AuditLog`。

已标明但未接通的部分：

- 注释写明 v1 未启用登录。用户与成员只是预留结构，业务代码没有创建用户或检查角色。
- 资源是 `Task.assignee` 字符串，没有 `TaskAssignee`。
- 没有基线表，没有扫描报告表。
- `Task.version` 有字段，更新语句没有按 version 做条件写入。
- `AuditLog` 没有操作者外键，影响信息放在 `payload` JSON 字符串里。

Prisma Client 生成到 `src/generated/prisma`（已 gitignore）。仓库没有 `prisma/migrations`，脚本是 `db:push` / `db:studio`。

### 3.7 目录与测试

- 页面在 `src/app`。
- 工作区组件在 `src/components/workspace`。
- 项目列表在 `src/components/project`。

测试只有排期与校验这两组 Vitest 单测，没有 Server Action、WBS 重编号或界面测试。近期提交为脚手架初始化加上当前这一版计划功能（`init`），没有更细的功能分批记录。

## 4 下一步开发建议

下列事项都对应代码或设计文档里已经露出、但尚未接上的缺口。

### 4.1 补上真实身份与权限

顶栏用户、退出和个人设置是静态界面；「资源 / 审计 / 用户」不可点击。`User`、`ProjectMember` 和 `Role`（OWNER / PM / MEMBER / VIEWER）已建模却未被 Action 使用。写操作目前任何人打开页面即可执行。应先接登录，再在 `runChange` 入口按项目角色拒绝越权，并让顶栏导航指向真实页面。

### 4.2 把已经写入的审计展示出来

`applyPlanChange` 会记 action、目标、已确认的规则编号和冲击摘要，但没有读取界面。审计页至少应按项目、时间倒序展示这些 payload，否则「确认后记入审计」在产品上不可见。

### 4.3 补齐并发控制

`Task.version` 已存在，更新没有 `where: { id, version }`，也没有冲突后的刷新提示。多人同时改同一项目时，后写会覆盖先写。设计文档里的乐观锁可以直接落在 `applyPlanChange` 上。

### 4.4 让汇总进度与引擎结果一致

`computeSchedule` 会按子节点工期加权算出汇总 `progressPct`。`persistSchedule` 不写该字段。`loadWorkspace` 展示的是库里的 `task.progressPct`。父节点进度因此不会随子节点填报更新。要么回写派生进度，要么在视图层改用本次排期结果。

### 4.5 用上已声明但未调用的 zod

依赖已安装，Action 仍是手写判断，和设计文档「字段格式交给 zod、业务规则交给 validatePlan」不一致。把 `CreateProjectInput`、`UpdateTaskInput` 等收成共享 schema，可避免前后端各写一套范围检查。

### 4.6 扩大测试面

排期与 V1–V4 有单测。事务回滚、WBS 重编号、缩进时的依赖转接、自动前级、初验点锚点不可删，都没有测试。这些分支集中在 `server/plan.ts` 与 `server/actions/task.ts`，适合先补集成测试，再考虑浏览器级流程：建项目 → 插任务 → 改工期 → 看到初验余量变化。

### 4.7 甘特图与本地预览

图是只读时间轴加点击编辑，没有拖拽改依赖，没有长列表虚拟化。引擎已经是纯函数，但每次编辑都等 Server Action。可在提交前用同一份 `computeSchedule` / `validatePlan` 做本地预览，减少「处理中」往返。虚拟化留到单项目任务量上来之后再做。

- 基线快照与对比
